A service account is an identity for software, such as a CI job or trading bot, with its own role and API keys in one workspace.

Send its key as `X-API-Key` ([Authentication](/authentication)), or exchange it for a short-lived bearer token with the standard OAuth 2.0 client-credentials grant, so any OAuth client library works.

**You need:** to be a workspace owner or admin who manages credentials, in a signed-in session. No API key or token can create another credential.

## Create a service account

<Steps>
  <Step title="Create the account">
    In the app, open **Identity & access**, then **Service accounts**. Select **Create service account**, enter a **Name** and choose a **Role**; **Description** and **Expires** are optional.
  </Step>

  <Step title="Copy its user ID">
    It is the `client_id` of the token request.
  </Step>

  <Step title="Create and store a key">
    Open the account, then **API keys**, and select **New key**. Enter a **Key name** and select **Create key**. Copy the key, the `client_secret` of the token request, to your secret manager, never source code or a tracked file: it is shown once.
  </Step>
</Steps>

Enabling or rotating a service-account key's request signing is a signed-in member's operation, never the account's own ([Rotate the signing secret](/authentication#rotate-the-signing-secret)).

### Its sponsor

Every service account has a sponsor: the member accountable for it, by default its creator.

- Its permissions are its role intersected with the sponsor's current permissions, checked on every request. If the sponsor's shrink, the account's shrink with them.
- When the sponsor stops being a current, unsuspended workspace member, the account's keys cannot trade from organisation wallets. Those orders, and later steps of trades already placed, are refused with `409 SERVICE_ACCOUNT_SPONSOR_NOT_CURRENT`. Set a current member as sponsor to resume.

## Exchange the key for a token

Send a form-encoded `POST /api/v1/oauth/token` ([RFC 6749, section 4.4](https://www.rfc-editor.org/rfc/rfc6749#section-4.4)). `client_id` and `client_secret` may go in an HTTP Basic `Authorization` header instead.

| Field | Value |
| --- | --- |
| `grant_type` | `client_credentials` |
| `client_id` | The service account's user ID. |
| `client_secret` | One of its API keys, the full `tfk_live_…` or `tfk_test_…` value. |

The answer is the standard token response:

| Field | Meaning |
| --- | --- |
| `access_token` | The bearer token. |
| `token_type` | `Bearer`. |
| `expires_in` | Seconds until the token expires, at most 900 (15 minutes). |
| `scope` | What the token may do, space-separated. |

There is no refresh token: exchange the key again before expiry. Keep tokens in memory only; the key is the credential to protect.

<OauthToken />

```json Output on test networks
{"token_type":"Bearer","expires_in":900,"scope":"compliance_read dashboard_read flow_read orders_read permission_requests_read permission_requests_write prices_read settlements_read trades_read"}
```

## Check what the token can do

`GET /api/v1/me` with the token returns `IntrospectionResponse` for the key it came from, as for that key sent as `X-API-Key` ([Send the key](/authentication#send-the-key)). It describes current authority, not a user profile or verification record.

| Field | Meaning |
| --- | --- |
| `authKind` | `apiKey`: the answer describes an API key. |
| `auth` | `oauthClientCredentials` for a token; `apiKey` for the key itself. |
| `keyId` | The key the token was exchanged from. |
| `workspaceId` | The one workspace the token works in. |
| `scopes` | What the token may do now: its issued scopes, narrowed by the key's and its sponsor's current permissions. |
| `organisationWallets` | When present, the key's organisation-wallet trading authority. Its `blockedBy` is the code an organisation-wallet order would be refused with now ([Check what a key can do](/authentication#check-what-a-key-can-do)). |

`workspaceId` and `organisationWallets` may be absent or `null` when the key is bound to no workspace; rate limits and expiry are optional.

<OauthMe />

```json Output on test networks
{"authKind":"apiKey","auth":"oauthClientCredentials","keyId":"322229a8","workspaceId":"5f56c3dd-…","scopes":["compliance_read","dashboard_read","flow_read","orders_read","permission_requests_read","permission_requests_write","prices_read","settlements_read","trades_read"],"blockedBy":"VENUE_TRADE_SCOPE_REQUIRED"}
```

<Note>
Scopes can shrink while a token is valid. `/me` reads them live: call it again rather than trusting the token's `scope`.
</Note>

## Send the token

Send `Authorization: Bearer <access_token>` in place of `X-API-Key`. It works in the service account's workspace only.

<OauthCall />

```json Output on test networks
{"orders":[{"orderId":"ba5a2e31-…","kind":"basicTrade","status":"pending","terminal":false}]}
```

## When the exchange is refused

A refused exchange answers the RFC 6749 error body, `{"error", "error_description", "error_uri"}`, not the [JSON error body](/trade/errors#read-a-refusal) of other refusals.

| `error`, status | Cause and fix |
| --- | --- |
| `invalid_client`, 401 | The `client_id` or `client_secret` is wrong, or the key is not an active key of an active service account. Carries a `WWW-Authenticate: Basic` challenge. Check both values; create a new key if this one was revoked or expired. |
| `invalid_grant`, 400 | `grant_type` is missing, or the form is unreadable. Send the three fields, form-encoded. |
| `unsupported_grant_type`, 400 | `grant_type` is not `client_credentials`. |
| `unauthorized_client`, 400 | The key requires request signing or holds venue trading; `error_uri` ends with `#SIGNED_KEY_NOT_EXCHANGEABLE`. Use another key, or send this one as a signed `X-API-Key` ([Sign requests](/authentication#sign-requests)). |
| `temporarily_unavailable`, 503 | TetraFi could not read the account's current authority. Retry shortly. |

A key with request signing on is never exchanged: a bearer token cannot carry a request signature.

<OauthSignedRefused />

```json Output on test networks
{"status":400,"error":"unauthorized_client","error_uri":"https://tetrafi.mintlify.app/reference/error-codes#SIGNED_KEY_NOT_EXCHANGEABLE"}
```

An expired token is refused with `401` and `WWW-Authenticate: Bearer error="invalid_token"` ([RFC 6750](https://www.rfc-editor.org/rfc/rfc6750#section-3)): exchange the key again. A refused API key carries no challenge.
