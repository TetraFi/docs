This policy covers the integrator API: the operations in
[API reference](/reference/introduction), which are asset discovery, prices,
quotes and requotes, preflight, orders, and the order and quote-set reads. It takes effect
at launch. Until then the contract is still changing, and every change is listed in the
[changelog](/changelog).

## What we promise

After launch, a change to the integrator API is **additive**. We may:

- add an operation, an optional request field, a query parameter or a header;
- add a field to a response object;
- add a value to a response enum or a tagged union, or a new error code;
- add a status code to an operation, as long as it uses the error body below;
- make a request rule looser, for example by accepting a value that used to be refused.

We do not, without the deprecation process below:

- remove or rename an operation, field, value, header or code;
- change a field's type or meaning, or a code's HTTP status;
- make an optional request field required, or a request rule stricter;
- stop sending a response field we documented as always present.

## What your client should do

- **Ignore fields you don't know.** Response objects can gain fields at any time, so don't
  validate them as closed.
- **Treat unknown enum values as "other".** Every response enum and tagged union in the
  spec is marked `x-extensible-enum`. Handle the values you know, and give anything else
  a neutral fallback. For example, a quote source with an unknown `status` is a source you
  can't use. A `next` action with an unknown `kind` is a step you can't take
  automatically.
- **Handle unknown error codes by status.** Act on the codes you know, and treat any other
  code by its HTTP status class: retry a `429` or `503` after `Retry-After`, fix the
  request on any other `4xx`, and retry a `5xx` with backoff.
- **Send only documented request fields.** Request bodies stay strict: an unknown field
  answers `400 INVALID_REQUEST` naming it, so a typo never passes silently.
- **Discover values instead of hard-coding them.** Assets, chains and venues come from
  `GET /api/v1/assets` and from quote responses. A venue or asset can be added without
  any change to your code.

## The error body

Every refusal of an integrator operation, at every status, is one JSON object:

```json
{
  "error": "QUOTE_EXPIRED",
  "message": "This quote has expired. Request a new one.",
  "requestId": "r1-mvfqiqp1-0",
  "timestamp": 1792443399,
  "next": { "kind": "requote", "needs": [] },
  "details": { "retryAfter": "PT2S" }
}
```

- `error` is the stable code. Match on it, never on `message`.
- `message` is for people and may change.
- `requestId` equals the `X-Request-Id` response header. Quote it when you contact support.
- `next`, when present, is the way forward.
- `details`, when present, carries the code's detail. Its keys are camelCase and it can
  gain keys. On `429` and some `503` answers, `details.retryAfter` is an ISO 8601
  duration, and the `Retry-After` header carries the same wait in seconds.

The authentication, rate-limit, body-size and timeout refusals use this same body. One
parser reads them all.

## Retries and idempotency

`POST /api/v1/orders` takes an `Idempotency-Key` header, and API keys must send one. A
retry with the same key and the same body returns the first answer and never places a
second order. A different body under the same key answers `409 IDEMPOTENCY_CONFLICT`.
Refusals are not stored, so after one, fix the request and send it again. The OpenAPI
description of the header has the full rules.

## Deprecation

When something has to go after launch:

1. The changelog announces it, with a removal date at least 6 months away. A security fix
   may need a shorter window, and the notice says why.
2. Every affected response carries a `Deprecation` header (RFC 9745), a `Sunset` header
   with the removal date (RFC 8594), and a `Link: <…>; rel="deprecation"` header pointing
   to the notice. The spec marks the operation or field `deprecated: true`.
3. The replacement ships before the notice, so you can move at any point in the window.
4. On the sunset date, the old shape is removed.

## How we check ourselves

Each build regenerates the integrator spec and compares it with the spec published at the
last release. Any breaking difference by the rules above fails the build. Until launch the
check only reports, because the contract is still changing in place.
