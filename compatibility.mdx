This policy covers every operation in the integrator API,
[API reference](/reference/introduction). It takes effect at launch. Until then the
contract is still changing, and every change is listed in the [changelog](/changelog).

**Launch date: not yet declared.** The policy below takes effect on the date written here, and only
here.

At launch, the reference's `info.version` moves off `1.0.0-beta.1`.

It covers:

- the token exchange and the calling credential;
- asset discovery and prices, quotes and requotes;
- orders, trades and their settlement, and balances;
- venue accounts (deposits, credit and ledger);
- settlement windows, obligations, movements and the settlement plan;
- the fee schedule and workspace capabilities;
- webhooks and their event bodies.

## Versioning

The API is versioned by date. A version is named `YYYY-MM-DD`; the one supported version today is
`2026-11-17`.

<Accordion title="More on versioning">

- **Your key's pin.** Every API key records the version that was current when it was created.
  Requests from that key are answered in its pinned version. Rotating a key keeps its pin.
- **The header.** Send `TetraFi-Version: YYYY-MM-DD` to choose the version of one request. A value
  that is not exactly one supported date answers `400 API_VERSION_UNSUPPORTED` before anything runs;
  it is never replaced by another version. Without the header a key's request uses its pin, and a
  member session uses the current version.
- **The answer.** Every response names the version it was answered in, in its `TetraFi-Version`
  header (only the `400 API_VERSION_UNSUPPORTED` refusal carries none).
- **Webhooks.** Each webhook endpoint records the version current when it was created, and every
  body it receives carries it as `apiVersion`.
- **Upgrading.** When a new version ships, send its date in `TetraFi-Version` from your client to
  test it while your key stays on its pin. When your client is ready, create a new key (it pins the
  newest version) and retire the old one; recreate a webhook endpoint to move its bodies.
- **After launch,** an [additive](#what-we-promise) change reaches every version. A breaking change
  ships only as a new dated version, so a pinned key never sees it until you move.

</Accordion>

## What we promise

After launch, a change to an existing version is **additive**. A breaking change ships only as a
new dated [version](#versioning): a key pinned to an older version keeps that version's shape until
that whole version is retired through the [deprecation process](#deprecation).

| Change | Class | What you do |
|---|---|---|
| Add an operation, an optional request field, a query parameter or a header | Additive | Nothing |
| Add a field to a response object | Additive | Ignore unknown fields |
| Add a value to a response enum, or a new variant (discriminator value) to a response tagged union | Additive | Fall back on unknown values |
| Add a new error code | Additive | Handle by status class |
| Add a status code to an operation, using the [error body](#the-error-body) | Additive | Handle by status class |
| Make a request rule looser, e.g. accept a value that used to be refused | Additive | Nothing |
| Remove or rename an operation, field, value, header or code | Breaking | New version only; move before your version's sunset date |
| Change a field's type or meaning, or a code's HTTP status | Breaking | New version only; move before your version's sunset date |
| Make an optional request field required, or a request rule stricter | Breaking | New version only; move before your version's sunset date |
| Stop sending a response field documented as always present | Breaking | New version only; move before your version's sunset date |

Values are camelCase. Identifiers (permissions, API key scopes, workspace types) and values that
name stored records (fee treatment, funding and leg states, review reasons, approval and order
stages) are snake_case tokens and will not be renamed.

Before launch, a breaking change lands in place with no alias. Each one has a
[changelog](/changelog) entry saying it is breaking and what to change. Read the entries since
your last upgrade before you update a client.

## What your client should do

- **Ignore fields you don't know.** Response objects can gain fields at any time, so don't
  validate them as closed.
- **Treat unknown enum values as "other".** Every response enum and tagged union in the spec is
  marked `x-extensible-enum`. Handle the values you know, and give anything else a neutral fallback:
  - a quote source with an unknown `status` is a source you can't use;
  - a `next` action with an unknown `kind` is a step you can't take automatically.

  A tagged union (a `oneOf` told apart by `kind`, `status`, `state` or another tag) can gain a
  variant with a tag value you have not seen. Switch on the tag with a default branch that skips
  the value or treats it as "other"; never let an exhaustive match fail on it. The TypeScript SDK
  types every response union with an open member for such variants: narrow a known variant with
  `isVariant(value, 'kind', 'known')`. Request unions stay closed; send only documented variants.
- **Treat identifiers as opaque strings.** Every `id` and `…Id` field and path parameter is a
  string. Compare it as a string and store it as returned; don't parse it, validate it as a UUID or
  derive anything from its shape. Its format can change without notice.
- **Handle unknown error codes by status.** Act on the codes you know, and treat any other code by
  its HTTP status class:
  - `429` or `503`: retry after `Retry-After`;
  - any other `4xx`: fix the request;
  - `5xx`: retry with backoff.
- **Send only documented request fields.** Request bodies stay strict: an unknown field answers
  `400 INVALID_REQUEST` naming it, so a typo never passes silently.
- **Discover values instead of hard-coding them.** Assets, chains and venues come from
  `GET /api/v1/assets` and from quote responses. A venue or asset can be added without any change to
  your code.

## Pagination tokens

- `nextCursor` is an opaque continuation token. Return it unchanged as `cursor` for the same list,
  workspace and filters.
- Never decode, construct or edit it. Its private encoding is not part of the integrator contract.
- Tokens may expire, including after a server-key rotation or a deployment that changes the private
  format.
- An invalid or expired token answers 400. Restart from the first page without `cursor`.

## Permission request targets

A quote source's `fix` (`QuoteSourceFix`) and a refusal's `refusalFix` (`RefusalFix`) of kind
`requestPermission` name a `target`, a tagged union on `kind`. Since 2026-11-10 it has three values:

<Accordion title="More on permission request targets">

| `target.kind` | Fields |
|---|---|
| `walletRight` | `walletId`, `right` |
| `workspacePermission` | `permission` |
| `accountRight` | `accountId`, `right` (`transfer`, `approveTransaction` or `manageDestinations`): a right on a custody account named by its financial account id |

The addition is additive: `target.kind` and the rights are open enums. Treat an unknown `kind` as a
permission a member asks for in the app; its `approvers` and `existingRequest` still read as
documented.

</Accordion>

## Order identity and minimum receive

Order identity:

<Accordion title="More on order identity and minimum receive">

- Both order kinds carry one top-level `orderId`, accepted by `GET /api/v1/orders/{id}`.
- An Advanced order retains `order.orderId`; a Basic order retains `operation.operationId`. These
  nested resource identifiers are not aliases for a second order resource.
- The ordered by-quote recovery answer and `order.updated.data` carry that same canonical id.

Minimum receive:

- Read each quote card's `minReceiveRequired` boolean before ordering.
- When it is true, supply `minReceive`. Omitting it returns 400 `MIN_RECEIVE_REQUIRED` with
  `details.field: "minReceive"`.
- The flag describes existing admission, not a new restriction.
- A false flag does not grant permission to order: readiness, expiry and the card's `next` still
  apply.

</Accordion>

## The error body

Every refusal of an integrator operation, at every status, is one JSON object:

<Accordion title="More on the error body">

```json
{
  "error": "QUOTE_EXPIRED",
  "message": "This quote has expired. Request a new one.",
  "requestId": "r1-mvfqiqp1-0",
  "timestamp": "2026-10-19T22:16:39Z",
  "next": { "kind": "requote", "needs": [] },
  "details": { "retryAfter": "PT2S" }
}
```

| Field | Meaning |
|---|---|
| `error` | The stable code. Match on it, never on `message`. |
| `message` | For people; it may change. |
| `requestId` | Equals the `X-Request-Id` response header. Quote it when you contact support. |
| `next` | When present, the way forward. |
| `details` | When present, the code's detail. Its keys are camelCase and it can gain keys. On `429` and some `503` answers, `details.retryAfter` is an ISO 8601 duration, and the `Retry-After` header carries the same wait in seconds. |

The authentication, rate-limit, body-size and timeout refusals use this same body, so one parser
reads them all.

### Rate-limit headers

Every response counted by a finite limiter, including 2xx and 429, carries two headers, following
[draft-ietf-httpapi-ratelimit-headers-07, sections 3.1 and 3.5](https://www.ietf.org/archive/id/draft-ietf-httpapi-ratelimit-headers-07.html):

| Header | Example value | Meaning |
|---|---|---|
| `RateLimit-Policy` | `100;w=60` | Quota and window seconds |
| `RateLimit` | `limit=100, remaining=41, reset=19` | A structured dictionary |

- Values come from actual admission decisions.
- Of the applicable key, route and per-address policies, the one closest to exhaustion is reported
  (section 3.2): lowest remaining, then longest reset.
- On a limiter's 429, exactly the refusing policy is reported, with `remaining=0`.
- If a venue supplies a cooldown but no quota/window, the RateLimit headers are omitted rather than
  attributed to an unrelated policy.
- For a known refusing policy, `reset` equals `Retry-After` and the seconds in
  `details.retryAfter`.
- `reset` is the whole-second wait until quota next becomes available, not an epoch or a promise of
  a full token-bucket burst refill. A rolling window may restore quota incrementally.
- Missing headers mean no quota claim, never zero.

Bounded service and placement-capacity refusals use `429 RATE_LIMITED` with a typed admission cause
and a matching retry duration and header. They describe no quota or window, so they omit
`RateLimit` and `RateLimit-Policy`, even when an earlier key or route limiter accepted the request.

This pre-launch change of status from timeout/unavailable to 429 is recorded in the 2026-11-06
[changelog](/changelog) entry. The pre-launch `X-RateLimit-*` scheme is retired.

</Accordion>

## Retries and idempotency

These promises hold within a version; how to retry and recover is in
[Retries and recovery](/trade/orders#retries-and-recovery):

<Accordion title="More on retries and idempotency">

- `POST /api/v1/orders` takes an `Idempotency-Key` header, and API keys must send one.
  `POST /api/v1/quotes` takes an optional one.
- The same key and the same body return the first answer: never a second order, and no venue is
  asked again.
- A different body under the same key answers `409 IDEMPOTENCY_CONFLICT`.
- Refusals are not stored, and a streamed quote answer (`Accept: text/event-stream`) is never
  replayed.
- The OpenAPI description of the header has the full rules.

</Accordion>

## Cancellation

`POST /orders/{id}/cancel` accepts the GET order identifier and returns that same envelope with
`status: "cancelled"` and `terminal: true`. It is idempotent by order id. A key needs the
`orders_write` scope and an `Idempotency-Key`; a member session needs permission to place orders.
Advanced orders are not cancellable through this endpoint, and a refusal is 409
`ORDER_NOT_CANCELLABLE` with the current public status in `details.status`. No cancellation call
reaches a venue, and a deposit already credited remains the workspace's balance. Which orders can
be cancelled: [Cancel an order](/trade/orders#cancel-an-order).

## Order lifecycle

`POST /api/v1/orders` and `GET /api/v1/orders/{id}` return the same envelope:
`{kind, status, terminal, statusUrl, quoteId?, requestId?, order|operation}`.

<Accordion title="More on order lifecycle">

- `kind` is `advancedTrade` (nested `order`) or `basicTrade` (nested `operation`). For Basic
  trades, `{id}` is the operation id.
- `statusUrl` is always `/api/v1/orders/{id}`, including quote-order recovery and webhook data.
- Reading a placed order needs the `orders_read` scope on a key, or permission to view or place
  orders in a member session. Unknown, foreign and unreadable orders share 404 `ORDER_NOT_FOUND`;
  a key missing the read scope receives 403 `INSUFFICIENT_SCOPE`.
- States may be skipped: act on `terminal`, not on a particular sequence. The public `status` is an
  open, camelCase enum; nested native status fields retain their own vocabulary.
- `next` on an uncertain or review-required order (`wait` or `contact`) never authorizes another
  order or a funds movement; terminal orders carry none, and an unknown future kind is not an
  action to take automatically.

What each status means and how to follow an order: [Order status](/trade/order-status).

| status | Meaning | FIX OrdStatus analogue | terminal |
|---|---|---|---|
| `pending` | Accepted, nothing sent yet | A PendingNew | no |
| `working` | Sent; executing | 0 New / 1 PartiallyFilled | no |
| `filled` | Executed; settlement or delivery remains | 2 Filled | no |
| `settled` | Executed and settled, or no settlement applies | 2 Filled | yes |
| `unfilled` | Not filled, or never sent; nothing traded | 4 Canceled / C Expired | yes |
| `cancelled` | Cancelled before dispatch | 4 Canceled | yes |
| `failed` | Failed after it was sent; nothing more will happen, but it does not by itself prove nothing traded | 8 Rejected | yes |
| `refunded` | Funds returned to the payer | 4 Canceled | yes |
| `reviewRequired` | A person must review before it continues | 9 Suspended | no |
| `outcomeUnknown` | Venue outcome is being reconciled | none | no |
| `refused` | Refused by a pre-trade check before anything was sent; `operation.complianceRefusal` names why. Trade again with a new quote | 8 Rejected | yes |

Terminality comes from the order's durable product facts:

- Advanced escrow, resource-lock and deferred orders can still owe a claim after native `settled`.
  Route delivery and atomic venue orders need no separate claim.
- A failed fill that can recover remains nonterminal.
- Basic orders require final execution and final settlement/delivery, or no such legs.
- Review and unknown outcomes never mean terminal.

</Accordion>

## Webhooks

A workspace webhook receives a signed `POST` for each event it subscribes to. `order.updated` is
sent on every status change of an order placed in that workspace. How to verify, acknowledge and
deduplicate deliveries: [Receive order updates by webhook](/trade/webhooks).

<Accordion title="More on webhooks">

- The body is `{id, type, apiVersion, createdAt, data}`. For `order.updated`, `data` is
  `{orderId, kind, status, terminal, statusUrl}`; for `treasury.balance.low` and
  `treasury.balance.recovered`, it is `{ruleId, workspaceId, walletId, asset, units, available,
  threshold, direction, observedAt}`.
- If durable lifecycle facts are temporarily unavailable, `terminal` is omitted (never guessed) and
  `status` names the observed event.
- New `type` values and new fields can appear without notice, so ignore what you don't know.
- `apiVersion` is the version the endpoint pinned when it was created ([Versioning](#versioning)).
  A breaking change to a body ships only under a new version.
- Signatures follow Standard Webhooks (`webhook-id`, `webhook-timestamp`,
  `webhook-signature: v1,<base64>`, HMAC-SHA256 over `"<webhook-id>.<webhook-timestamp>.<raw request body>"`
  keyed with the `whsec_<base64>` secret); no legacy
  headers are sent, and a rotation dual-signs for 24 hours. For an older hex secret, use
  `"whsec_" + Buffer.from(oldSecret, "hex").toString("base64")` in the reference library.
- Delivery is at least once, retried after 5 s, 30 s, 10 min, 1 h, 6 h and 24 h without a `2xx`;
  the body's `id` stays the same across retries and redeliveries.

</Accordion>

## Deprecation

After launch, nothing is removed or changed incompatibly inside a version. A removal or breaking
change reaches only callers on a newer dated version (see [Versioning](#versioning)); a key pinned to
an older version keeps its shape until that version is retired. Retiring a whole version is the only
thing announced this way:

<Accordion title="More on deprecation">

1. **Notice.** The changelog announces the version's retirement, with a sunset date at least 6
   months away. A security fix may need a shorter window, and the notice says why.
2. **Marking.** Every response answered in the retiring version carries:
   - a `Deprecation` header (RFC 9745);
   - a `Sunset` header with the retirement date (RFC 8594);
   - a `Link: <…>; rel="deprecation"` header pointing to the notice.
3. **Replacement.** The newer version ships before the notice, so you can move at any point in the
   window: test it with `TetraFi-Version`, then create a key pinned to it.
4. **Retirement.** On the sunset date, the retired version is no longer served. Move keys and
   webhook endpoints pinned to it to a supported version before then.

</Accordion>

## How we check ourselves

- Every change to the integrator spec is compared with the spec last released to each environment.
- Ordinary builds report a breaking difference by the rules above, without stopping.
- A release to beta or production is refused when it contains a breaking difference that is not
  approved for that release and listed in the changelog.
