These rules hold on every endpoint, so implement them once. The examples order nothing.

Example outputs across these docs were recorded on test networks, so some show test chain ids such as `eip155:84532` (Base Sepolia). Your answers carry the chains your venues reach ([Coverage](/supported-chains)).

## Requests

| Rule | Detail |
| --- | --- |
| Base URL | `https://api.tetrafi.io`. Every path starts with `/api/v1`. |
| Credentials | `X-API-Key` on every request, plus a signature when request signing is on ([Authentication](/authentication)). |
| Workspace | The key implies its workspace, so it needs no `X-Workspace-Id`; a path under `/api/v1/workspaces/{workspaceId}/` names it. A header you send anyway must be the key's own. |
| Version | Optional `TetraFi-Version: YYYY-MM-DD`. Without it, a key's requests use the version it pinned when created ([Versioning](#versioning)). |
| Bodies | JSON, sent with `Content-Type: application/json`. |

## Values

| Value | Form |
| --- | --- |
| Amounts | Decimal strings such as `"10.0147"`, never JSON numbers: parse with a decimal type, not a float. |
| Times | RFC 3339, in UTC: `"2026-10-30T00:40:13.162Z"`. |
| Durations | ISO 8601: `"PT2S"`. |
| Networks | CAIP-2 network ids such as `"eip155:8453"`, in fields and parameters named `network`. |
| Field names | camelCase: `expiresAt`. |
| Ids | Opaque strings with no promised format (not UUIDs): store and compare them whole. |
| Enumerations | Open sets that can gain values, such as `"status": "answered"`. Treat a value you do not know as other ([Conventions](/reference/conventions#values)). |

<Accordion title="Precision, ids, variants and lifecycle">
| Value | Rule |
| --- | --- |
| Amount precision | At most the asset's decimals. More is refused with `400 AMOUNT_PRECISION_EXCEEDED` (`details.field`, `details.decimals`, `details.allowed`) before any quote or funding check. |
| Ids | Never parse or validate their shape. Example: `"q_01JAY7Q5M3ZK8V2N4R6T8W0XYB"`. |
| Variants | A record whose shape depends on a tag (`kind`, `status`), such as `"kind": "basicTrade"`, can gain variants. Branch on the tag, read a known variant's fields only inside its branch, and keep a default branch for one you do not know. In the TypeScript SDK (not published yet; see [SDK and samples](/sdk)), narrow with `isVariant(value, tag, name)`: comparing the tag with `===` does not narrow to that variant's fields. |
| Lifecycle | A record's lifecycle is always `status`, such as `"status": "settled"`; an observation of a figure read from a venue or ledger keeps `state` (`observed`, `notStarted`, …). |
</Accordion>

## Paging

A list that pages takes `limit` and answers `nextCursor`. Send it back unchanged as `cursor` until `nextCursor` is absent or `null`.

| Rule | Detail |
| --- | --- |
| Opaque tokens | Never decode, construct or edit them; their encoding is not part of the contract. |
| Same list only | Use a token only for the same workspace, list and filters. |

<Accordion title="Expired tokens, snapshot lists and page sizes">
| Rule | Detail |
| --- | --- |
| Expired or invalid token | Tokens may expire, including after a server-key rotation or private-format deployment. An invalid or expired authenticated cursor answers 400: restart without `cursor`. |
| Snapshot lists | A list with a snapshot contract may answer `409 CURSOR_STALE` after the underlying selection changes: restart from its first page. |
| `GET /api/v1/assets` | 1 to 200 assets a page. |
| `GET /api/v1/orders` | Up to 20 orders a page; a page can hold fewer than `limit`, even none, while more follow. |
</Accordion>

## Errors

| Rule | Detail |
| --- | --- |
| One body | Every refusal carries `error`, `message`, `requestId`, `timestamp`, `docUrl`, and `next` and `details` when they apply. |
| One status per code | Each code has one HTTP status. `docUrl` links its entry in the [error-code reference](/reference/error-codes). |
| Match on `error` | Never on `message`. |

[Errors and refusals](/trade/errors) shows how to read one.

## Request ids

Every response carries `X-Request-Id`; a refusal repeats it as `requestId`. Quote it to support.

<Accordion title="Send your own request id">
  Send `X-Request-Id` (up to 64 letters, digits, `-` and `_`) to trace a request in your logs and ours; the response echoes it. An invalid id is replaced with a generated UUID, which the response carries instead.

  <ConventionsRequestId />

  ```json Example output
  {"requestId":"conventions-1793895638","rateLimitPolicy":"1;w=3","rateLimit":"limit=1, remaining=0, reset=3"}
  ```
</Accordion>

## Rate limits and idempotency

| Rule | Detail |
| --- | --- |
| Rate limits | Every limit answers `429` with `Retry-After` ([Rate limits](/reference/rate-limits)). |
| Idempotency | Send an `Idempotency-Key` with every `POST /api/v1/orders`, and with `POST /api/v1/quotes` to make a quote retry safe. A retry with the same key and body returns the first answer, with `Idempotent-Replayed: true` ([Retries and recovery](/trade/orders#retries-and-recovery), [Retry a quote](/search/how-it-works#request-and-read-quotes)). |

## Read several resources at once

`POST /api/v1/batch` runs up to 20 reads in one round trip, each as its own `GET` by the same caller. A signed API-key request cannot be batched, so a signing key sends its reads separately.

<Accordion title="Items, rate limit, answers and refusals">

| Rule | Detail |
| --- | --- |
| Items | 1 to 20 `{id, method, url}`. `method` is `GET`; `url` is the path and query of a `GET` operation in this reference, such as `/api/v1/orders?limit=20`. |
| Authority | Each item runs as its own `GET` by the same caller: same permissions, scopes, workspace checks, body and error body. |
| Rate limit | Each item counts as one request, all taken before any item runs. A `429 RATE_LIMITED` refuses the whole batch. |
| Answer | `200` once admitted, items in request order. Items are independent, not atomic. |
| Item answer | Each item returns `id`, `status`, `etag`, `body` and, when sent, `headers` (`Retry-After`, `Cache-Control`). An item that had not answered by the batch's deadline answers `504 SOURCE_TIMEOUT` inside the `200`: read it again on its own. |
| Limits | Item bodies total at most 8 MiB (past it an item answers `413 BATCH_RESPONSE_TOO_LARGE`), and at most 200 reads with related reads (past it `429 SUB_REQUEST_BUDGET_EXHAUSTED`). |
| Refused as a whole | A malformed batch, more than 20 items, a non-`GET` item, an unknown operation, or a stream, export or file read. `details.itemId` names the item. |

</Accordion>

## Versioning

The API is versioned by date. The one supported version today is `2026-11-17`. Every API key is answered in the version current when it was created; `TetraFi-Version: YYYY-MM-DD` chooses one request's version.

<Accordion title="Pins, requests, webhooks and upgrading">
| Rule | Detail |
| --- | --- |
| Your key's pin | Every API key records the version current when it was created, and its requests are answered in that version. |
| One request | Send `TetraFi-Version: YYYY-MM-DD` to choose the version of that request. A value that is not exactly one supported date answers `400 API_VERSION_UNSUPPORTED` before anything runs. |
| The answer | Every response names its version in a `TetraFi-Version` header. |
| Webhooks | Each endpoint records the version current when it was created; every body carries it as `apiVersion`. |
| Upgrading | Test a newer version by sending its date in `TetraFi-Version`, then create a new key, which pins the newest version, and retire the old one. |
</Accordion>

<Accordion title="What can change within a version">
  Within a version, changes are additive: new operations, optional fields, headers, enumeration values, variants and error codes. A breaking change ships only as a new dated version. Until the launch date in the [Compatibility](/compatibility) policy, a change can still rename or remove something in place; each one is listed in the [Changelog](/changelog) with what to change.
</Accordion>
