---

During the pilot the API can still change, and every change a client can see is listed here with what to do. From general availability on, changes follow the [compatibility policy](/compatibility): additive within a version, and a breaking change only as a new dated version that your key reaches when you choose ([Versioning](/reference/conventions#versioning)).

<Update label="2026-11-22" description="Hosted wallets and the organisation spelling">
  - **Breaking.** The binding target kind (`FundsTargetKind`) `organizationWallet` is now `hostedWallet`: a wallet run by a provider for your workspace. Send `hostedWallet` where you named a target kind, and read it in binding defaults and target views.
  - **Breaking.** The schemas `OrganizationSetupCreatorTradeGrant` and `OrganizationSetupCreatorTradeGrantState` are `OrganisationSetupCreatorTradeGrant` and `OrganisationSetupCreatorTradeGrantState`. Field names and values are unchanged; only generated type names move (the SDK follows).
</Update>

<Update label="2026-11-22" description="Order steps: a swap is a venue fill with a kind">
  - **Breaking.** A Uniswap swap step in an order's step history (`operation.steps[]`) reads `summary.purpose` `venueFill`, like every venue's fill step; `uniswapExactInputSingle` and `uniswapExactInputPath` are gone. Match `venueFill`.
  - A venue's fill step carries `summary.kind`: `swap` for a swap inside one chain, null on every other step. The set is open: treat a kind you do not know as other.
</Update>

<Update label="2026-11-21" description="Pairs: stable ids, pages, fields and one vocabulary for unread sources">
  - **Breaking.** [`GET /api/v1/pairs`](/api-reference/trading/list-pairs) is always paged: 100 pairs by default, `limit` up to 1000 (a larger value is read as 1000), and `limit=0` is `400 INVALID_REQUEST`. Follow `nextCursor`, or narrow the list with `sellAsset` or `buyAsset`.
  - Each pair has a stable `id`, `SELL~BUY` (for example `USDC~ETH`). `fields=` returns only the fields you name; `id`, `sell` and `buy` are always kept. Every page carries an `ETag` for `If-None-Match`.
  - **Breaking.** `unreachable[].reason` on `GET /api/v1/pairs` and `GET /api/v1/assets` is one open set: `notReadYet` (read again in a few seconds), `unavailable`, or `listedAfterConnection` (a venue that lists its pairs only once you connect it). The venue's own code moves to `details.ownerCode`. Match on `reason`, not on the code.
  - A venue that lists its pairs only once you connect it is a `listedAfterConnection` entry of `availability=connectable`, and no longer hides the list's `hint`.
  - Optional pair fields (`sellNetwork`, `buyNetwork`, `legs`, `routes`, `connectableVenues`, `hint`) are absent rather than `null`.
</Update>

<Update label="2026-11-21" description="One status per error code">
  - **Breaking.** `WALLET_NETWORK_UNKNOWN` is always `400`: the request named a network TetraFi cannot place. When the wallet itself sits on such a network, the answer is `409 WALLET_RECORDED_NETWORK_UNKNOWN`.
  - **Breaking.** A key that trades venues (`venue_trades_write`) but has no bounded IP allowlist is refused `403 VENUE_TRADE_KEY_IP_ALLOWLIST_MISSING` when it calls. `400 VENUE_TRADE_IP_ALLOWLIST_REQUIRED` now only answers creating or editing such a key. Give the key an allowlist of your own networks.
  - **Breaking.** An order's recorded refusal of its next step reads `COMPLIANCE_RECHECK_NOT_CONFIGURED` when the compliance re-check before that step is not set up.
</Update>

<Update label="2026-11-20" description="List the pairs you can trade">
  - New: [`GET /api/v1/pairs`](/api-reference/trading/list-pairs) lists the directed pairs your workspace can trade now, each with the routes (venue and where it executes) that serve it. `availability=connectable` lists the pairs only a venue you have not connected serves.
</Update>

<Update label="2026-11-20" description="Every refusal names what to do; deposit history reads several assets and networks at once">
  - Every refusal from the integrator API carries `details.remedy`: what to do next, in words, from [Error codes](/reference/error-codes). It is for people and logs; keep matching on `error` and `details.remediation`.
  - A quote source that gives no price always has a `detail`, even when the venue named only a reason, so no source reads as unavailable without its cause.
  - **Breaking.** Venue deposit history takes `asset` and `network` as optional comma-separated lists (`asset=USDC,USDT&network=eip155:1,eip155:8453`); leaving one out reads every asset or network the account offers for deposit, in one request with one cursor. Each item names its `asset` and `network`, and a pair that could not be read is one `unreachable` entry. The form that read exactly one asset and one network per request is gone: send the lists, or nothing.
</Update>

<Update label="2026-11-20" description="Designed to grow, second pass: states instead of booleans, objects instead of strings, and schemas that say what is always sent (rolling out)">
  - **Breaking.** A quote search's `venueAsked` boolean is `answeredFrom`: `venues` when at least one venue was contacted, `cache` when every quote came from cached prices. Treat other values as new sources.
  - **Breaking.** Each `source.preferredWallets` value is an object, `{wallet, signer?}`, like `source.tradingWallets`; a bare string is refused 400 `INVALID_REQUEST`.
  - **Breaking.** A route leg is referenced by its `legId`, never by position: an order transaction's `legIndex`, a repricing offer's `legIndex` and the `legIndex` of the `signNextLeg` and `retryNextLeg` next actions are `legId`, the id the quote published in `legs[].legId`. A payment leg's own id is always `tradeLegId`: on the `provideDestination` and `payoutFeeRose` next actions, `TradeLegFacts`, `FiatLegArrival` and `PayoutRecipientConfirmation`, where it was `legId`.
  - **Breaking.** A quote leg's `relayMode` is `deliveredBy`.
  - **Breaking.** An `address` destination's `calldata` is `data`, in the request, the resolved destination and the request echo.
  - **Breaking.** An asset's `coingeckoId` is `externalIds.coingecko`, so other directories can be added beside it.
  - **Breaking.** A trade fee row's `gasPriceWei` is `gasPrice`, `{amount, asset}` in the network's own coin, or `null`.
  - **Breaking.** Error codes no longer name a provider. `ACROSS_FEE_SHARE_EXCEEDS_25_PERCENT` and `RELAY_FEE_SHARE_EXCEEDS_25_PERCENT` are one `409 BRIDGE_FEE_SHARE_TOO_HIGH`, with `details.provider` and `details.limitPercent`. `CCTP_FEES_UNAVAILABLE` is `BRIDGE_FEES_UNAVAILABLE`, with `details.provider`. `STABLEFX_SIGNING_GRANT_REQUIRED` is `VENUE_SIGNING_GRANT_REQUIRED`, with `details.venueId`.
  - **Breaking.** The re-check before a route's next step is named by what failed: `RELAY_RECHECK_UNAVAILABLE` is `COMPLIANCE_RECHECK_UNAVAILABLE`, `RELAY_SUBJECT_UNRESOLVED` is `COMPLIANCE_SUBJECT_UNRESOLVED`, `RELAY_CONTEXT_UNRESOLVED` is `COMPLIANCE_CONTEXT_UNRESOLVED` and `RELAY_FUNDER_UNRESOLVED` is `FUNDING_SOURCE_UNRESOLVED`. Statuses and retry advice are unchanged.
  - **Breaking.** A blank or incomplete `GET /api/v1/assets` filter answers `400 ASSET_FILTER_BLANK` or `400 ASSET_FILTER_INCOMPLETE`, naming the parameter in `details.field`, instead of `INVALID_REQUEST`.
  - Every code the reference names is now in [Error codes](/reference/error-codes), including the codes sent as values inside a successful read.
  - The schemas now say which fields are always sent: a field is either required and `null` when unknown, or optional and never `null`. The wire did not change; a generated client gets tighter types.
</Update>

<Update label="2026-11-19" description="Signing with your own wallet: camelCase step values, wallet holds and the signing window (rolling out)">
  - **Breaking.** An order's step history (`operation.steps[]`) sends camelCase values: `summary.purpose` (`token_approval` is `tokenApproval`, `uniswap_exact_input_single` is `uniswapExactInputSingle`, `bridge_deposit` is `bridgeDeposit`, and the rest alike), `authority.kind` (`headlessGrant`, `ownerCeremony`, `browserWallet`), a `GRANT_CAP_EXCEEDED` refusal's `cap` (`perTrade`) and `transaction.status` (`approvalPending`, `providerOutcomeUnknown`, `nonceConsumedElsewhere`, `signedNotBroadcast`; one-word values unchanged). Every set is open: treat an unknown value as other.
  - **Breaking.** Each `source.tradingWallets` value is an object, `{wallet, signer?}`; a bare string is refused 400 `INVALID_REQUEST`, and the top-level `source.signer` is gone. Send `{"wallet": "<id or address>"}` per network.
  - **Breaking.** A client-signed order holds its wallet on a network for its whole run, not only while a step is open: a second order answers 409 `SIGNING_WALLET_BUSY` naming the holder in `details.orderId`, including two orders placed at once.
  - **Breaking.** Past a step's `signBy`, `declined` answers 410 `SIGNING_STEP_EXPIRED` and records nothing; before it, once the wallet's nonce moved past the step's, 409 `SIGNING_STEP_NOT_OPEN`.
  - **Breaking.** Quoting a wallet you sign yourself needs the right to trade from it: a member without the Trade right on the wallet (a Viewer) is refused 403 `SIGNING_WALLET_NOT_ALLOWED` with `details.cause`. A key the order's steps would refuse is refused at `POST /api/v1/orders`, before any order exists. Details: [Sign with your own wallet](/trade/sign-with-your-own-wallet).
</Update>

<Update label="2026-11-19" description="Error codes: one form, one permission code, camelCase reasons">
  - **Breaking.** Codes end in what is wrong: `INVALID_AMOUNT` is `AMOUNT_INVALID`, `INVALID_CURSOR` is `CURSOR_INVALID`, `INVALID_LIMIT` is `LIMIT_INVALID`, `INVALID_WORKSPACE_ID` is `WORKSPACE_ID_INVALID`, `UNKNOWN_ASSET` is `ASSET_UNKNOWN`, `UNKNOWN_VENUE` is `VENUE_UNKNOWN`, `UNKNOWN_CHAIN` is `NETWORK_UNKNOWN`, and `MISSING_WORKSPACE` is `WORKSPACE_REQUIRED`.
  - **Breaking.** `VALIDATION_ERROR` is gone: a malformed request is `400 INVALID_REQUEST`, with `details.field` naming the input.
  - **Breaking.** A missing permission is always `403 INSUFFICIENT_PERMISSION`, naming it in `details.permission` (or `details.anyOf`). `ACCESS_FORBIDDEN` and `INSUFFICIENT_WORKSPACE_PERMISSION` are gone; `INSUFFICIENT_SCOPE` is unchanged.
  - **Breaking.** Every `details.reason` is camelCase, the signing reasons included. A venue's refusal of an order is `400 VENUE_CLIENT_ERROR`, with our reason in `details.reason` and the venue's own code in `details.venueCode`.
  - **Breaking.** Faults inside TetraFi are `500 INTERNAL_ERROR` or `503 SERVICE_UNAVAILABLE`, with the failed part in `details.reason`. `LEDGER_JOURNAL_UNAVAILABLE` is `LEDGER_READ_UNAVAILABLE`, and the settlement plan's `SETTLEMENT_PROJECTION_*` read entries are `SETTLEMENT_FACTS_*`.
</Update>

<Update label="2026-11-19" description="Designed to grow: legs, steps and signers by id; signing with your own wallet and ordering a price row (all rolling out)">
  - Rolling out over the next releases: the shapes below name legs, steps and signers, so routes over several venues, steps signed by different parties, non-EVM signing and broker trading (all coming, not live) arrive later as additions only. What your client should tolerate: [Designed to grow](/reference/conventions#designed-to-grow).
  - Quote legs: each item of `legs[]` has a `legId` (`leg_0` on a one-leg quote), its own `sell` and `buy` (`{asset, amount}`) and an optional paying `source`. **Breaking.** `legs[].venue` can be `null`, on a leg no venue runs: read it as optional.
  - Steps: every step (`signing.firstStep`, `next.step`, `operation.steps[]`) names its `signer` (`you`, `tetrafi` or `venue`) and its `legId`; a step you sign also lists, in `covers`, the legs its signature authorises. `operation.steps` lists every step of the order. Sign only a step whose `signer` is `you`. The reference publishes the step as named variants by `type`: `transaction` (EVM) and `typedData` (EIP-712); other networks come as new `type` values. The wire is unchanged.
  - `signing.signers` lists every party that signs a quote, `{signer, address, network, legIds}`, one entry today; `signing.address` is the first paying signer's address.
  - Each of an order's `fills` names its `legId` and `network`; the order's `venueId` and `venueName` summarise a single-venue order.
  - `POST /api/v1/orders` takes `onBehalfOf`, for broker trading (coming). It must be the `onBehalfOf` the quote was requested with, or the order is refused `403 DIRECT_USER_MISMATCH`.
  - `tradingSource` and each `sourceOptions` candidate carry an optional `owner`, `{kind, id}`, with `kind` `workspace`, `member` or `principal`. A wallet `family` can be `bitcoin`, which nothing trades yet.
  - A refusal's `details` can name `legId`, `stepId` and `venueId`. `details` keys are per code and can grow.
  - `GET /api/v1/me` answers the key's pinned `apiVersion` and `venueAccounts` (`{"kind": "all"}` today), and each organisation-wallet grant its `rights` (`["trade"]` today).
  - A webhook endpoint shows its `apiVersion`, and `PATCH …/webhooks/{webhookId}` with `apiVersion` moves it to another supported version without recreating it.
  - **Breaking.** `order.updated` `data.next` takes the order's `next` shape: `stepId` and `sequence` are present only when `kind` is `sign`. `data.terminal` is always present.
  - Rolling out, not live yet: `POST /api/v1/orders` also takes `{kind: "stream", priceId, minReceive | slippageBps}` to order a [Live prices](/search/prices) row. TetraFi checks the `priceId` (`PRICE_ID_INVALID`, `PRICE_EXPIRED`), asks the venue for that exact size, and runs the order like a quote order of that venue. A price outside your limit is refused with `details.remediation` `widenLimit`.
  - Signing with your own wallet is rolling out, not live yet; the full contract is on [Sign with your own wallet](/trade/sign-with-your-own-wallet).
  - Signed-in members use the same three routes as API keys; the step route takes a session bearer token as well as a key. An External wallet named in `source.preferredWallets` makes the quote `signing.mode` `you`.
  - Without `firstStep`, the order opens with `next.kind` `sign` for step 1. Without `minReceive`, the order is bound by the minimum the quote's own step was drafted with.
  - New refusals `SCREENING_UNAVAILABLE` (503; a screening provider failure is never a refusal), `DELIVER_TO_NOT_SIGNING_WALLET` and `DELIVER_TO_NOT_REGISTERED` (422), and `SIGNING_WALLET_UNSUPPORTED`. Every 503 on this path carries `details.cause`. `SOURCE_NOT_OWNED`, `PERSONAL_TARGET_NOT_ALLOWED`, `SIGNING_WALLET_UNSUPPORTED` and `ADVANCED_SOURCE_ACCOUNT_UNAVAILABLE` are now `definitelyNotSent: true`.
  - The order reads `clientSigned` and its step history in `operation.steps`; `order.updated` fires whenever `next` changes; a new outcome `nonce_used_elsewhere` means a different transaction was mined at the pinned nonce.
  - The next step opens at 1 confirmation; a terminal outcome is never delayed for finality or rewritten. Steps by venue, as measured live, including Bebop's and Circle StableFX's order ([Steps by venue](/trade/sign-with-your-own-wallet#the-step-object)).
  - **Breaking.** The error code `BROWSER_STEP_CONTINUATION_REFUSED` is gone: only the app's own wallet-step route returned it, and that route is retired. A member's External-wallet step is answered on `POST /api/v1/orders/{orderId}/steps/{stepId}`, like every other step.
  - At an on-chain Basic venue that needs no key and is still being set up, the first quote you sign records your wallet as the venue's activation wallet; if nothing else is missing, the venue is ready on that same quote.
  - **Breaking.** Webhook bodies are `{id, type, apiVersion, occurredAt, data}`: `createdAt` is now `occurredAt`, when the event happened. In `data`: `order.updated` names `settlementStatus` (was `settlementState`); `settlement.*` `statementVersion` and `credit.updated` `termsVersion` are integers, not strings; `credit.updated` says what changed in `change` (was `status`). Each published event's `data` has its own schema in the API reference ([Webhooks](/trade/webhooks)).
  - **Breaking.** Webhook event names are `<area>.<resource>.<status>` in at most three parts, and an event that mirrors a status ends with that status. Renamed: `compliance.event` -> `compliance.other`, `compliance.sanctions.flag_added` -> `compliance.sanctions_flag.added`, `api_key.expiring_soon` -> `api_key.expiring`, `direct_user.verification.verified` -> `direct_user.verification.passed`, `treasury.approval.denied` -> `treasury.approval.declined`, `treasury.step.*` -> `treasury.run_step.*`, `treasury.bank_deposit.history_*` -> `treasury.deposit_history.*`, and the agent events (`treasury.agent_envelope.*`, `treasury.agent.stopped`, `treasury.agent_session_signer.*`, `treasury.agent.sponsor_changed`, `treasury.agent_payment.*`) ([Webhook events](/reference/webhook-events)). Your webhooks were moved to the new names.
  - **Breaking.** A webhook subscribes only to events TetraFi sends: any other name is `400 WEBHOOK_EVENT_UNKNOWN` with the accepted names in `details.acceptedKeys`, and `WEBHOOK_EVENT_RETIRED` is gone. Names that were never sent (`member.invited`, `member.joined`, `lp.*`, `kyb.*`, `kyc.expiring`, `settlement.failed`, `settlement.retried`, `settlement.disputed`, `affiliation.*`, `bilateral.*`, `direct_user.updated`, `direct_user.invited`, `direct_user.suspended`) were dropped from your webhooks.
</Update>

<Update label="2026-11-18" description="Create wallets with an API key, find assets by venue or address, and signing with your own wallet (rolling out)">

  - New wallet creation: `POST /api/v1/workspaces/{workspaceId}/wallets` starts an organisation wallet with the owners who approve it, `GET …/wallets` and `GET …/wallets/{walletId}` follow it, and `POST …/wallets/{walletId}/cancel` withdraws it. Each owner approves on their own signing page; an API key never approves ([Create an organisation wallet](/trade/create-wallet)).

</Update>

<Update label="2026-11-17" description="Dated versions, quote retries, open variants, status and network names, and credit for every account">
  - **Dated versions.** The API version is `2026-11-17`. Each API key and webhook endpoint pins the version current when it was created; send `TetraFi-Version: YYYY-MM-DD` to choose one request's version (`400 API_VERSION_UNSUPPORTED` for any other value), and every response names its version in the same header. Webhook bodies carry the endpoint's version as `apiVersion` ([Versioning](/reference/conventions#versioning)).
  - `POST /api/v1/quotes` takes an `Idempotency-Key`: a retry with the same key and body returns the first answer and asks no venue again ([Retry safely](/search/how-it-works#request-and-read-quotes)).
  - A record tagged by `kind` or `status` can gain variants without a new version: keep a default branch for a tag you do not know ([Conventions](/reference/conventions#values)). Identifiers are opaque strings; the reference no longer marks them `uuid`.
  - **Breaking.** Lifecycle fields read `status`, not `state`: the settlement plan, windows (filter with `status`) and obligations, a trade's obligations, a credit `observation`, quote order recovery (`GET /api/v1/orders/by-quote/{quoteId}`) and venue balances.
  - **Breaking.** `GET /api/v1/prices` takes `sell.network` and `buy.network` instead of `sell.chain` and `buy.chain`.
  - **Breaking.** More lifecycle fields read `status`, not `state`: a venue key's `withdrawalGate`, venue withdrawals and deposit declarations, a bank deposit's transition, deferred-settlement obligations (the order's own status there is now `orderStatus`), a deposit's source screening, a deferred statement's reconciliation and a deposit intent.
  - **Breaking.** A network is one CAIP-2 `network`: an asset display drops `chainId` and `chainRef` for `network`; a funds target lists `networks` (was `chains`); venue deposit options, deposit instructions (also a quote's `fund` step) and deposit history name `network` (was `chainRef`), and the deposit reads take `network=` instead of `chainRef=`; a quote card's venue `execution.network` replaces `execution.siteChain`. Wallet and account requests no longer accept `chain` in place of `networkRef`, `networkFamily`, `networkLabel` or `network`.
  - **Breaking.** `treasury.balance.low` and `treasury.balance.recovered` use the standard `{id, type, apiVersion, createdAt, data}` envelope, with their fields under `data` ([Webhook events](/reference/webhook-events)).
  - **Breaking.** A quote's, order's and venue trade's `settlement` names its mode `settlementMode` (`window` or `anytime`), as documented; it had been sent as `settlement_mode`.
  - New `GET /api/v1/workspaces/{workspaceId}/venue-account-credit` lists every venue account's credit in one call, or those named in `venueAccountId`; an account that cannot be read is one `unreachable` entry ([Settlement and credit](/trade/settlement-and-credit#monitor-credit-per-account)).
  - The settlement plan takes `venueAccountId`, answers `nextTransitionAt` (re-read then instead of polling), and each window carries `carries` and `minimumOutcome`. An account whose settlement facts are not ready is its own `failedReads` entry, such as `SETTLEMENT_PROJECTION_PENDING`.
  - A settlement window read takes `include=` (`terms`, `schedules`, `obligations`, `nudges`, `payments`, `matches`, `statements`, `messages`) and answers them in `included`.
  - A batch item that has not answered by the batch's deadline answers `504 SOURCE_TIMEOUT` inside the `200`.
  - **Breaking.** Venue accounts and connections read `tradingStatus` and `withdrawalStatus` (`active`, or `paused` by your workspace's control; treat another value as not active) instead of the booleans `tradePaused` and `withdrawalPaused` ([Balances and fees](/trade/balances)).
  - **Breaking.** `GET …/venue-accounts/{venueAccountId}/settlement/schedules` is a paged list: `items` and `nextCursor`, with `limit` (1 to 100, default 20) and `cursor`. The schedule in effect, a pending change and the next window moved to the new `GET …/venue-accounts/{venueAccountId}/settlement/schedule-selection` ([Settlement and credit](/trade/settlement-and-credit)).
  - **Breaking.** A quote leg's `product` is an object tagged by `kind`: `{"kind": "cctpBridge"}` instead of the string `"cctpBridge"`, and `{"kind": "fiatVenue", "venueId": …, "direction": …}` or `{"kind": "workspaceVenue", "venueId": …, "movement": …}` instead of a nested `fiatVenue` or `workspaceVenue` object.
  - **Breaking.** `POST /api/v1/quotes` refuses a body field it does not know, at any depth, with `400 INVALID_REQUEST` naming the field. An `Idempotency-Key` that is malformed or sent with `Accept: text/event-stream` answers `400 IDEMPOTENCY_KEY_INVALID`.
  - A workspace path (`/api/v1/workspaces/{workspaceId}/…`) names the workspace, and the reference no longer lists `X-Workspace-Id` on it. An API key needs no workspace header anywhere; one you send must still name the key's own workspace ([Authentication](/authentication#send-the-key)).
  - The TypeScript SDK narrows a tagged record with `isVariant(value, tag, name)`; comparing the tag with `===` does not narrow to that variant's fields ([Conventions](/reference/conventions#values)).
  - The [compatibility policy](/compatibility) now says a breaking change ships only as a new dated version, and deprecation applies to retiring a whole version.
  - **Breaking.** A reconciliation's ledger amount is tagged by `status` (`reported` with its `amount`, or `notReported`), not `state`. The funding-deposit refusals `FUNDING_DEPOSIT_FAILED` and `FUNDING_DEPOSIT_NOT_CREDITED` name the deposit's Run status in `details.runStatus`, not `details.state`.
  - Each organisation wallet granted to a key (`GET /api/v1/me`, `organisationWallets.grants`) states its `family` and its `networks`, each switched on or off, or `networksUnreadable` when they could not be read ([Before you trade](/before-you-trade)).
</Update>

<Update label="2026-11-16" description="One name per field, slippage limits, and uncertain retries">
  - **Breaking: one name per field.** Every field that had an older twin now has only its new name:
    - `asset` replaces `currency` and `assetId` everywhere, including credit amounts and terms, ledger and bank reads, quote funding instructions and a quote card's pay-from source, and refusal `details`; `assetSymbol` replaces `symbol`.
    - Order legs name chains `sourceNetwork` and `destNetwork`; each order transaction names its chain `network`, or `networkUnsupported` (the raw chain id) for a chain TetraFi does not list, instead of `chainId`.
    - `GET /api/v1/assets` reports a partial list in `unreachable` (no `eligibility`), and its registry snapshot needs `include=registry`.
    - The trade list answers `totalCount` (no `total`, `limit` or `scope`), and what it could not hold in `unreachable` (no `coverage`, `excludedKinds` or `latestTradeAt`).
    - `GET /api/v1/orders` no longer sends `scanLimitReached`: follow `nextCursor` until it is `null`.
    - Settlement window matches answer `items` (no `matches` or `readAt`), and a window page has no `readAt`.

<Update label="2026-11-09" description="A nonce on every signed write">

    - Stop building the Basic trade's address from your workspace, connection and operation ids.
    - Match `401 AUTH_REQUIRED` for every authentication failure, and read the cause in `details.reason`, for example `MISSING_CREDENTIALS`, `INVALID_API_KEY` or `SIGNATURE_INVALID`.
    - Match the renamed codes: `QUOTE_PRICE_MOVED` (was `PRICE_MOVED_BEYOND_PROTECTION`), `VENUE_FIRM_QUOTE_LIMITED` (was `FIRM_QUOTE_LIMITED`), `QUOTE_ALREADY_ORDERED`, `QUOTE_ID_INVALID` for a malformed quote id, and `WALLET_SIGNATURE_REQUIRED` for a missing wallet signature on an order.
    - Read `docUrl` on any refusal: it links the code's entry in the [error-code reference](/reference/error-codes).
    - Deliver trade output to an address or one of your own accounts: no trade can deliver to a payee.

    An API key implies its workspace:

    An API key is bound to the workspace it was created in, and every request it sends now works in that workspace without `X-Workspace-Id`.

    What to change:
    - Stop sending `X-Workspace-Id` with an API key, or keep sending it: when present it must be the key's own workspace, or it is refused with `403 WORKSPACE_SCOPE_MISMATCH`.
    - A signed-in member's session still sends `X-Workspace-Id`. Without it, the request is refused with `400 MISSING_WORKSPACE`.
    - Read a placed order's status at the `statusUrl` its `POST /api/v1/orders` answer returns, instead of building the address yourself.
    - Filter `GET /api/v1/workspaces/{workspaceId}/trades` with its camelCase parameter names only, for example `nextActor`, `dateFrom`, `amountMin` and `sortBy`. The snake_case names are refused with `400`.
  </Accordion>
  <Accordion title="2026-10-29: Trading source and funding replace bind and binding">
    A quote request names what a trade executes with in `source`, and where its output goes in a top-level `deliverTo`. Each quote states its trading source and its funding. The old `bind`, `binding` and `bindingOptions` fields are gone, with no aliases.

    What to change:
    - Read `sourceOptions` where you read `bindingOptions`. It is listed on the quote set and on each quote. Candidates carry `financialAccountId`, `kind`, `displayName` and `isDefault` instead of `id` and `label`.
    - Send `source.tradingWallets` (CAIP-2 chain id to `financialAccountId`) where you sent `bind.wallets`, `source.venueAccountId` where you sent `bind.account`, and `source.fundingAccountId` where you sent `bind.bankAccount`.
    - Send `deliverTo` at the top level of the request or requote, not under `bind`. Its kinds are `financialAccount`, `payee` and `address`.
    - Read each quote's `tradingSource`, `fundingModel`, `fundingAccount`, `settlement` and `deliverTo` where you read `binding`. A quote with no usable source carries `sourceRefusal`.
    - Read a quote's `location` as `{ "kind": … }` only: `singleChain`, `crossChain`, `offChain` or `mixed`.
    - On a `walletRefused` source, read `recovery.defaultWallets` and send it as `source.tradingWallets`, where you sent `recovery.defaultBinding` as `bind`.

    - Match `SOURCE_NOT_OWNED` (403) where you matched `BINDING_NOT_OWNED`. It now refuses a `deliverTo` or `source.fundingAccountId` naming a wallet or account you cannot use.
    - A trading wallet in `source.tradingWallets` that a venue account has not linked is no longer refused. That venue reads `unavailable` with the reason `tradingSourceNotLinked`, and the others still quote.

    The other source refusal codes keep their names, for example `BINDING_NOT_ON_CHAIN`. [Wallets and accounts](/trade/wallets-and-accounts) covers the new fields.
  </Accordion>
  <Accordion title="2026-10-27: Consistent refusals, order status and source reasons; New developer docs">
    Consistent refusals, order status and source reasons:

    Every refusal of a quote, price, order, preflight, asset or order-status request, at every status, is now one JSON object:

    | Field | What it is |
    |---|---|
    | `error` | The stable code. Match on it. |
    | `message` | A sentence for people. It can change. |
    | `requestId` | The same value as the `X-Request-Id` response header. Quote it to support. |
    | `timestamp` | When the refusal was made, in Unix seconds. |
    | `next` | The way forward, when there is one. |
    | `details` | The code's detail, when there is any. Keys are camelCase and can be added. |

    What to change:
    - Read `requestId` where you read `traceId` before.
    - Read waits from `details.retryAfter`, an ISO 8601 duration such as `PT2S`. The `Retry-After` header still carries the same wait in seconds.
    - Fields a refusal used to send at its top level now sit under `details`.
    - A request body that is too large now answers JSON, `413 REQUEST_BODY_TOO_LARGE`, instead of plain text.
    - A missing or empty `X-Workspace-Id` answers `400 MISSING_WORKSPACE` everywhere. A malformed one answers `400 INVALID_WORKSPACE_ID`.
    - Send credentials on `GET /api/v1/orders/{orderId}`. Without them, you get `401 MISSING_CREDENTIALS` before any order lookup. This one is rolling out: until it reaches a deployment, a read without credentials answers `404 ORDER_NOT_FOUND`.
    - Read order `status` as a string, including `"failed"`. Failure details are in `failure.phase`, `failure.code` and `failure.message`, not inside `status`.
    - Source reasons on quotes and prices are camelCase tokens, for example `pairNotServed` instead of `pair_unsupported` and `apiKeyOrganisationWalletScopeRequired` instead of `API_KEY_ORGANISATION_WALLET_SCOPE_REQUIRED`.
    - Match `receiveExactUnsupported` when a source cannot quote a fixed receive amount. Quotes and prices now use the same token. Read it from `reason`, or from `detail` on a `filteredOut` row.

    The [error-code reference](/reference/error-codes) lists every declared refusal and source reason. The `Idempotency-Key` rules for `POST /api/v1/orders` are now documented in full: see [Idempotency](/trade/orders#retries-and-recovery).

    New developer docs:

    These docs now describe one API for search, quotes, requotes and orders, with a runnable sample on every page. They start from the [Quickstart](/quickstart).

    The separate RFQ API, Router API, Price API and Trade History API pages are gone. Their old addresses redirect to the pages that replace them.
  </Accordion>

  <Accordion title="2026-10-17: Quotes by asset pair, requotes, and orders by quote id">
    A quote request names the asset you pay and the asset you receive, not chains or wallets: `POST /api/v1/quotes` with `pay`, `receive`, `amount` and `side`. Every quote states where it executes and how firm it is.

    - Changing a quote's wallet, account or route, or turning an indicative price executable, is a requote: `POST /api/v1/quotes` with `requote` set to the quote id. See [Requotes and expiry](/search/firmness-and-lifetime#requote-a-quote).
    - `POST /api/v1/orders` takes the quote id. The server holds the quote's terms, so you never send them back. See [Orders](/trade/orders).
    - `GET /api/v1/assets` lists what your workspace can trade, and `GET /api/v1/prices` returns indicative prices without asking any venue for a quote.
