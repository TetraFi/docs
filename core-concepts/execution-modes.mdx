---
title: "Execution Modes"
description: "Choose between API-submitted and self-broadcast settlement across TetraFi's APIs."
---

Both the RFQ API and Router API expose two execution modes. The mode arrives on each quote candidate as `executionMode`, and preflight returns the exact `nextActions` for the candidate you selected.

## Wallet Broadcast (`executionMode: walletBroadcast`)

You broadcast the settlement transaction yourself. Preflight returns the prepared transaction in `nextActions` with `actor: userWallet`.

**Flow:** Quote → Preflight → Sign & Broadcast the prepared tx

**Best for:** Solvers, aggregators, liquidators, and any integration that already manages its own transaction submission pipeline - and candidates that settle through an external venue or bridge.

**Key properties:**

* You pay gas
* No further interaction with TetraFi's API is required to land the trade
* The prepared transaction encodes the exact quoted terms - broadcast it as returned

## API Submit (`executionMode: apiSubmit`, native settlement)

TetraFi submits the settlement transaction on your behalf. You sign the EIP-712 `escrow-v0` order payload from the quote and POST it to the orders endpoint. The user never broadcasts a transaction.

**Flow:** Quote → Preflight → Sign EIP-712 order → POST `/orders` → Track via `GET /orders/{id}` or WebSocket

**Best for:** Wallets, super-apps, and consumer-facing products where users shouldn't think about gas or RPC endpoints.

**Key properties:**

* TetraFi handles on-chain submission
* Funds move only under the signed order's terms, through the escrow's delivery-or-refund path
* Requires an EIP-712 signature and order submission (use an `Idempotency-Key` header on the POST)

## Side by Side

|                  | Wallet broadcast                 | API submit                          |
| ---------------- | -------------------------------- | ----------------------------------- |
| `executionMode`  | `walletBroadcast`                | `apiSubmit`                         |
| Who submits tx   | You broadcast via your RPC       | TetraFi submits on-chain              |
| Gas cost         | Paid by taker                    | Abstracted away from the user       |
| Funding          | Direct from your wallet          | Escrow lock (Permit2 / EIP-3009 / resource lock) |
| Signing          | Standard transaction signing     | EIP-712 `escrow-v0` order signature |

## How Each Product Applies Them

While both APIs share the same execution modes, there are differences in how the modes apply:

### RFQ API

RFQ quotes are firm with **no last look** - every returned quote is a cryptographically signed, executable commitment, and settlement runs through the escrow's delivery-or-refund guarantee. A quote that cannot deliver refunds your escrowed funds instead of leaving you stuck. Handle the typed rejection classes on submission (expiry, integrity, eligibility) rather than mid-settlement failures.

See the [RFQ Order Submission guide](/rfq-api/guides/gasless-execution) for the full RFQ signing and submission flow.

### Router API

Execution mode varies **per candidate**: native TetraFi settlement candidates use `apiSubmit`, while candidates settling through external venues or bridges use `walletBroadcast`. Always read `executionMode` and the preflight `nextActions` from the candidate you selected rather than assuming a mode.

See the [Router API Quickstart](/router-api/quickstart) for both flows with complete code examples.
